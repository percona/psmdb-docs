## Release highlights

### General Availability of Percona Server for MongoDB 8.3

Percona Server for MongoDB {{ page.meta.version }} marks the General Availability (GA) of the 8.3 release series. Previous 8.3 releases were available as a technical preview and intended for testing only. Starting with this release, Percona Server for MongoDB 8.3 is production-ready and fully supported for use in production environments.

Percona Server for MongoDB {{ page.meta.version }} is now the latest, default and recommended version of Percona Server for MongoDB. It is the most performant and feature-rich version of Percona Server for MongoDB ever released.

### MongoDB Database Tools are distributed as a separate tarball

Starting with this release, MongoDB Database Tools (`mongodump`, `mongorestore`, `mongoexport`, `mongoimport`, and others) are no longer included in the Percona Server for MongoDB binary tarball. If you install Percona Server for MongoDB from tarballs, download the MongoDB Database Tools tarball separately from the [Percona Downloads :octicons-link-external-16:](https://www.percona.com/downloads/){:target="_blank"} website.

This change aligns the distribution of MongoDB Database Tools with how MongoDB Shell (`mongosh`) is already distributed. It also allows us to deliver tool updates, including security fixes, independently of the server releases.

If you install Percona Server for MongoDB from RPM or DEB packages, nothing changes for you: MongoDB Database Tools are installed as before.

## Upgrade recommendation

Percona Server for MongoDB {{ page.meta.version }} is the latest recommended version of Percona Server for MongoDB. We recommend **upgrading to version {{ page.meta.version }}** to benefit from the backup and checkpoint fixes included in MongoDB 8.3.13.

## Known issues

This section describes known issues in Percona Server for MongoDB {{ page.meta.version }} and their resolution status.

- [SERVER-136961 :octicons-link-external-16:](https://jira.mongodb.org/browse/SERVER-136961){:target="_blank"}: If a node has an unclean shutdown for any reason and then restarts to perform a [file copy based initial sync](../fcbis.md), the node crashes each time it restarts and cannot complete initial sync without manual intervention.

    To recover a node in a self-managed deployment, do one of the following:

    - Restart the node with the `initialSyncMethod` parameter set to `logical`.
    - Delete the contents of the node's `dbPath` directory, then restart the node to begin a new file copy based initial sync.

## Changelog

### Improvement

- [PSMDB-1944](https://perconadev.atlassian.net/browse/PSMDB-1944): MongoDB Database Tools packages are now built independently of Percona Server for MongoDB packages. This allows tool updates, including security fixes, to be prepared without rebuilding the server packages.

- [PSMDB-2182](https://perconadev.atlassian.net/browse/PSMDB-2182): Improved telemetry for x.509 certificate authentication. x.509 is used by default for internal authentication between members of replica sets and sharded clusters, so telemetry previously reported it as enabled on almost every instance. Telemetry now reports x.509 usage for client authentication separately from its use for internal cluster authentication.

### Bugs fixed

- [PSMDB-2126](https://perconadev.atlassian.net/browse/PSMDB-2126): Fixed an issue where streaming a backup to Google Cloud Storage through its S3-compatible API failed. The issue was caused by the upgrade of the AWS SDK for C++ to version 1.11.471, which added empty checksum elements to multipart upload requests that Google Cloud Storage rejects.

## Security fixes from upstream MongoDB

The severity categories below follow [CVSS scores :octicons-link-external-16:](https://nvd.nist.gov/vuln-metrics/cvss){:target="_blank"} version 4.0.

### High severity
- [SERVER-131412 :octicons-link-external-16:](https://jira.mongodb.org/browse/SERVER-131412){:target="_blank"} ([CVE-2026-104004 :octicons-link-external-16:](https://www.cve.org/CVERecord?id=CVE-2026-104004){:target="_blank"}): Collection validators using collation-accepting expressions can crash MongoDB Server on insert
  
  MongoDB Server's collection validation feature may not properly handle certain expressions stored in a validator. In some cases, this can cause the server process to stop running when a document is later inserted. The behavior can occur for authenticated users with write access. 
  
- [SERVER-131411 :octicons-link-external-16:](https://jira.mongodb.org/browse/SERVER-131411){:target="_blank"} ([CVE-2026-104005 :octicons-link-external-16:](https://www.cve.org/CVERecord?id=CVE-2026-104005){:target="_blank"}): Incorrect authorization in MongoDB Server router for bulk writes to system namespaces
  
  A security issue was discovered in MongoDB mongos (the sharded cluster router) where an authenticated user with `readWrite` privileges could crash the mongos process by crafting a specially formed aggregation pipeline. The issue leverages an internal aggregation stage that lacks proper authorization checks despite being intended for internal use, allowing a subsequent stage to be forced to execute on the router under conditions it was not designed to handle. This results in an unhandled fatal error that causes the mongos process to immediately abort, resulting in denial of service for all clients routed through the affected mongos instance.

- [SERVER-130431 :octicons-link-external-16:](https://jira.mongodb.org/browse/SERVER-130431){:target="_blank"} ([CVE-2026-96299 :octicons-link-external-16:](https://www.cve.org/CVERecord?id=CVE-2026-96299){:target="_blank"}): Missing Authorization Check on Internal Aggregation Stage in MongoDB Server mongos Leads to Denial of Service
  
  A security issue was discovered in MongoDB mongos (the sharded cluster router) where an authenticated user with `readWrite` privileges could crash the mongos process by crafting a specially formed aggregation pipeline. The issue leverages an internal aggregation stage that lacks proper authorization checks despite being intended for internal use, allowing a subsequent stage to be forced to execute on the router under conditions it was not designed to handle. This results in an unhandled fatal error that causes the mongos process to immediately abort, resulting in denial of service for all clients routed through the affected mongos instance.

### Medium severity

- [SERVER-132946 :octicons-link-external-16:](https://jira.mongodb.org/browse/SERVER-132946){:target="_blank"} ([CVE-2026-96297 :octicons-link-external-16:](https://www.cve.org/CVERecord?id=CVE-2026-96297){:target="_blank"}): MongoDB Server may disclose process memory via a crafted `$_internalApplyOplogUpdate` aggregation pipeline
  
  A use-after-free issue in the `$_internalApplyOplogUpdate` aggregation stage could expose unrelated data from server memory in query results. An authenticated user with read privileges could trigger the issue by combining the stage with a batch size of `0`. The server process could also terminate unexpectedly.

- [SERVER-134618 :octicons-link-external-16:](https://jira.mongodb.org/browse/SERVER-134618){:target="_blank"} ([CVE-2026-103965 :octicons-link-external-16:](https://www.cve.org/CVERecord?id=CVE-2026-103965){:target="_blank"}): Fixed values in MongoDB Server $bucket stage may be misread as field references
  
  An issue in the `$bucket` aggregation stage could cause constant values to be interpreted as field references during internal query rewriting. Under certain conditions, an authenticated user with read access could receive field values that the query did not intend to return.
